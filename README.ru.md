# SLI Platform — Security Log Intelligence

[English version](README.md)

SLI собирает и анализирует данные безопасности для расследований: события
Windows, контекст каталога, удалённый доступ и наблюдения рабочих станций.
Ядро на Python обеспечивает приём данных, идентификацию, хранение, контроль
доступа, исполнение заданий, отчёты и расследования. Встроенные плагины поставляют
модули сбора, нормализацию, правила и представления для AD/контроллеров домена,
GPO, VPN/удалённого доступа (включая NPS/RADIUS) и рабочих станций.

Windows-агенты читают разрешённые источники и передают ограниченные пакеты по
HTTPS. Ядро регистрирует агентов, проверяет их через mTLS и назначает модули.
SLI только читает обследуемые системы; доступ к источникам и сбор настраиваются
явно. Установка сервера сама по себе не включает сбор.

## Архитектура

Первая бета устанавливается нативными Debian-пакетами и управляется systemd.
PostgreSQL работает на хосте.
Стек включает HTTPS API с интерфейсом React/TypeScript, сервисы миграций и
резервного копирования, воркеры обработки собранных данных, проекций, семантики,
состояния сущностей, жизненного цикла хранения, снимков AD и удалённого доступа.

- **PostgreSQL 18** — основная runtime-БД для оперативных данных, идентичностей,
  прав доступа, состояния заданий и истории миграций.
- **Агенты** получают URL сервера, публичную цепочку доверия и назначенные
  политики; им не нужны пароли БД.
- **Ядро и плагины** разделяют общие механизмы и предметные знания.

## Быстрая установка — первая бета, Debian 13

Нужен чистый **Debian 13 amd64**, sudo, 4 ядра, 8 ГБ RAM, интернет,
локальная ext4 или XFS, диск от 40 ГБ и **не менее 20 GiB свободно после
установки пакетов**. Отдельный раздел для БД не нужен. Имя сервера должно
разрешаться с компьютера администратора и Windows-агента; можно использовать IP.
Разрешите входящий TCP 443 в своём firewall. Другой PostgreSQL на этом
сервере не поддерживается процедурой свежей установки. Для сбора нужен один
Windows 10 / Server 2016 или новее с правами локального администратора.

1. Получите у поставщика **полный комплект беты Debian 13 amd64**;
   агент .NET получите или соберите отдельно в шаге 6. Сверьте контрольные суммы
   по доверенному каналу.
   Распакуйте комплект и перейдите в каталог с `.deb`. Он должен включать
   `sli-host`, `sli`, `sli-rollback-hold`, `sli-release-*`, `sli-runtime-*`,
   `sli-server-dotnet` и закреплённые внешние зависимости, включая PostgreSQL 18.
   Одних исходников недостаточно. Публичный APT-репозиторий и подпись
   пакетов в этот этап не входят; не подключайте непроверенный репозиторий.
2. Обновите список пакетов дистрибутива:

   ```sh
   sudo apt update
   ```

3. Установите весь комплект:

   ```sh
   sudo apt install --fix-broken ./*.deb
   ```

   APT устанавливает зависимости и защитный пакет до сервера БД.
   Пакеты не запускают SLI и не создают владельца. `sli-host` запрещает создание
   чужого `main`-кластера; установка не форматирует диск.
4. Выполните **`sudo sli-setup`** и введите имя/IP и порт (Enter — **443**).
   Для автоматизации, например:

   ```sh
   sudo sli-setup --non-interactive --server sli.example.org --port 443
   ```

   Замените пример своим именем и локальным IP; для установки только по IP
   достаточно `--server <IP>`. Создаются site.toml, секреты, TLS с SAN для имени
   и IP, CA агентов, службы и каталог `/var/lib/sli-db`, подключённый в
   `/srv/sli-db`.

   Новая установка слушает все IPv4-адреса (`0.0.0.0`), а при доступном dual stack
   также IPv6 (`::`). Смена DHCP-адреса не оставляет listener на старом IP.
   Health использует loopback; его адреса включены в SAN сертификата.
   Явный `--bind 192.0.2.10` ограничивает HTTPS одним адресом;
   для локального reverse proxy используйте `--bind 127.0.0.1` и явно настройте
   доверенные прокси. Требования аутентификации и HTTPS сохраняются.
   Серверу нужен статический IP или постоянное DNS-имя. Сертификат выпускается
   на имя/IP при установке и IP, определённые тогда через DNS. После смены IP
   обновите DNS и сохраните прежний DNS URL (при wildcard bind).
   **`sudo sli-setup --server <новый-IP>` не перевыпускает сертификаты:** смена
   сохранённых имени сервера, bind или порта даёт `native_setup_configuration_conflict`.
   При установке только по IP нужно сохранить/вернуть исходный статический IP;
   автоматического пути смены адреса/сертификата установленного сервера в бете нет.
   Существующая установка сохраняет прежний bind;
   не меняйте только `site.toml` и не удаляйте сертификаты/квитанции установки.
5. Скопируйте публичный CA `/var/lib/sli/tls-ca.crt` на свой компьютер по
   доверенному каналу, сверьте напечатанный SHA-256 DER и импортируйте CA в
   доверенные корневые сертификаты браузера/ОС. Повторно получить отпечаток на Debian:

   ```sh
   openssl x509 -in /var/lib/sli/tls-ca.crt -outform DER | sha256sum
   ```

   Откройте адрес SLI из вывода установки, войдите с логином и паролем `admin`
   и задайте новый пароль длиной от 12 символов. Команда
   `sudo sli-setup --reset-admin-password` возвращает пароль `admin`, отзывает
   сессии владельца и требует сменить пароль при следующем входе. Имя владельца сохраняется.

   Если подбор пароля заблокировал вход активированного владельца, выполните
   в интерактивной root-консоли сервера:

   ```sh
   sudo sli-setup --owner-recovery <имя-владельца>
   ```

   На свежей установке укажите `admin`, после обновления укажите прежнее имя
   владельца. Введите показанный одноразовый код вместе с действующим паролем
   в форме входа. Код действует 10 минут; выпуск нового отменяет предыдущий.
   Команда не сбрасывает пароль и не снимает блокировку обычного входа.
   Восстановление доступно только активному владельцу платформы.
6. Используйте **агент .NET**, служба `SLIAgentNet`. Ручной
   [workflow agent-msi](.github/workflows/agent-msi.yml) собирает готовый
   неподписанный MSI. Скачайте `sli-agent-dotnet-msi-<полный-commit>` из
   **Artifacts** успешного запуска (хранятся 14 дней) либо получите тот же комплект
   у поставщика беты. Внутри — `SliAgent.msi`, `SliAgent-publish-win-x64.zip` и
   `SHA256SUMS`. Сверьте оба файла с доверенными контрольными суммами; распакуйте
   portable ZIP в `publish`, где непосредственно лежит `SliAgent.exe`.
   Публичная загрузка через releases не настроена.
   Для собственной сборки подходящего комплекта на Windows нужны PowerShell 7,
   .NET SDK **10.0.113**, MSVC Build Tools **14.44.35207** и Windows SDK
   **10.0.26100.0** по стандартным путям из
   [Build-RegistrationCA.ps1](agent-dotnet/tools/Build-RegistrationCA.ps1).
   Из корня репозитория (restore требует доступа к источникам пакетов):

   ```powershell
   .\agent-dotnet\tools\Build-Msi.ps1
   .\agent-dotnet\tools\Test-MsiTables.ps1 -Msi .\artifacts\agent-dotnet\SliAgent.msi -PublishDirectory .\artifacts\agent-dotnet\publish
   Get-FileHash .\artifacts\agent-dotnet\SliAgent.msi -Algorithm SHA256
   ```

   MSI содержит self-contained win-x64: на целевой машине установленная .NET не нужна.
   MSI не подписан; сверьте SHA256 по доверенному каналу поставки.
   На **одном целевом Windows-компьютере** откройте PowerShell от администратора,
   без transcript:

   ```powershell
   $ErrorActionPreference = 'Stop'
   New-Item -ItemType Directory -Force C:\SLI-Bootstrap | Out-Null
   icacls.exe C:\SLI-Bootstrap /inheritance:r /grant:r '*S-1-5-18:(OI)(CI)F' '*S-1-5-32-544:(OI)(CI)F'
   if ($LASTEXITCODE -ne 0) { throw 'Cannot protect bootstrap directory' }
   ```

   Скопируйте `SliAgent.msi`, полный каталог `publish` и **публичный** серверный
   `tls-ca.crt` в `C:\SLI-Bootstrap` по доверенному каналу.
   Сверьте скопированный CA с отпечатком из setup и подготовьте идентичность
   **на этом компьютере**, до установки:

   ```powershell
   $ca = [Security.Cryptography.X509Certificates.X509Certificate2]::new('C:\SLI-Bootstrap\tls-ca.crt')
   $sha = [Security.Cryptography.SHA256]::Create()
   ([BitConverter]::ToString($sha.ComputeHash($ca.RawData))).Replace('-', '').ToLowerInvariant()
   $sha.Dispose()
   $ca.Dispose()
   & C:\SLI-Bootstrap\publish\SliAgent.exe prepare
   ```

   Сравните напечатанный хеш CA с SHA256 (DER) из шага 5; при несовпадении остановитесь.
   `prepare` выводит публичные `host_id` (UUID) и `key_fingerprint`, сохраняя ключ
   в `%ProgramData%\SLI\AgentNet\state`, который будет использовать служба.
   Не запускайте подготовку на сборочном компьютере и не переносите закрытую
   идентичность между компьютерами. Войдите как `admin` и откройте
   **Агенты → Ручная регистрация для поддержки → Регистрация нового агента**,
   введите эти два публичных значения и нажмите **Создать токен регистрации**
   (по умолчанию TTL 900 секунд). Необязательное имя для замены оставьте пустым:
   это новый агент. На целевой машине вставьте токен в скрытый запрос до истечения TTL:

   ```powershell
   $token = Read-Host 'Enrollment token' -AsSecureString
   try {
       [IO.File]::WriteAllText('C:\SLI-Bootstrap\enrollment.token',
           [Net.NetworkCredential]::new('', $token).Password, [Text.Encoding]::ASCII)
   } finally { $token.Dispose(); Remove-Variable token }
   $msi = Start-Process msiexec.exe -Wait -PassThru -ArgumentList @(
       '/i', 'C:\SLI-Bootstrap\SliAgent.msi', '/qn', '/norestart',
       'SERVER_URL=https://sli.example.org',
       'CA_FILE=C:\SLI-Bootstrap\tls-ca.crt',
       'TOKEN_FILE=C:\SLI-Bootstrap\enrollment.token'
   )
   if ($msi.ExitCode -notin 0, 3010) { throw "MSI exit code: $($msi.ExitCode)" }
   Get-Service SLIAgentNet
   ```

   Замените `SERVER_URL` на HTTPS-адрес из setup (без `/app` и пути API).
   MSI запускает службу; она регистрируется автоматически и удаляет файл токена
   после сохранения идентичности. Дальнейшие check-in и доставка используют mTLS.
   Поддерживаемые свойства подключения: `SERVER_URL`, `TOKEN_FILE` или `ENROLL_TOKEN`,
   `CA_FILE` или `CA_FINGERPRINT` (SHA256 DER сертификата CA, 64 hex), необязательное
   `INSTANCE_NAME` (`[a-z0-9][a-z0-9_-]{0,47}`, должно совпадать с токеном).
   Для этой одиночной ручной регистрации не задавайте `INSTANCE_NAME`.
   `ENROLL_TOKEN` поддерживается, но раскрывает токен при записи командной строки
   процесса; используйте защищённый `TOKEN_FILE`. Сохраните `CA_FILE` по указанному
   пути: он остаётся источником доверия службы. Программа устанавливается
   в `%ProgramFiles%\SLI\AgentNet`.
7. В **Агентах** найдите строку своего хоста и свежее **Последнее подключение**
   (heartbeat). Через **Действия** назначьте **Рабочие станции** (`sli.workstations`)
   для станции, выберите нужные категории событий и возобновите сбор, если он
   приостановлен. Для DC используйте `sli.windows.ad-dc` и разрешённые каналы.
   Дождитесь совпадения запрошенной и применённой ревизий политики и подтверждения
   активного сбора в строке агента. Убедитесь, что Windows-аудит включён и служба
   имеет права чтения; создайте разрешённое тестовое событие входа.
   Откройте **Журнал событий** за этот интервал и проверьте событие своего хоста.
   Heartbeat подтверждает связь, полученное событие — сбор. При отсутствии события
   смотрите диагностику каналов/доставки в строке и журнал Windows **Application**,
   источник `SLIAgentNet` (безопасные коды диагностики).

8. Удаление: **Установленные приложения → SLI Agent .NET** либо PowerShell
   от администратора с исходным соответствующим MSI:

   ```powershell
   $remove = Start-Process msiexec.exe -Wait -PassThru -ArgumentList @(
       '/x', 'C:\SLI-Bootstrap\SliAgent.msi', '/qn', '/norestart'
   )
   if ($remove.ExitCode -notin 0, 3010) { throw "MSI exit code: $($remove.ExitCode)" }
   ```

   MSI останавливает и удаляет `SLIAgentNet`; настройки подключения и локальная
   идентичность сохраняются для переустановки. Код 3010 требует перезагрузки.

HTTPS операторов и mTLS агентов используют один порт **443**: дополнительный
открытый порт агентам не требуется. На нестандартном порту укажите его и в URL MSI.
Проверьте `sudo systemctl status sli.target sli-health.service` и после перезагрузки
повторите вход. При ошибке setup пишет причину словами; детали-коды находятся в
`sudo journalctl -t sli-setup`, состояние служб — в `systemctl --failed`.

### Нативные резервные копии

Проверьте ежедневное расписание: `sudo systemctl list-timers sli-backup.timer`.
Создать набор восстановления сейчас: `sudo sli-native-backup capture`.
Результат — `/var/backups/sli/native/last-result.json`; настроенный внешний том
копий SLI подключает в `/var/backups/sli`.
`backup_created` подтверждает создание и проверку целостности, но не успешное полное
изолированное восстановление. До его подтверждения сохраняйте прежние проверенные наборы.

### Переустановка с сохранением данных

На том же подготовленном сервере сохраните полный комплект БД, настроек,
секретов, CA агентов, registry в `/var/lib/sli` и проверенного recovery.
Из каталога согласованного нового комплекта Debian выполните:

```bash
sudo apt remove sli
sudo apt install ./*.deb
sudo sli-setup --reuse-existing
```

Удаление останавливает SLI и его БД, сохраняя данные. Установка пакетов только
подготавливает новый candidate. Setup запускает проверенный новый координатор:
проверка сохранённой установки → fence → checkpoint с проверочным восстановлением
в изоляции → миграции → acceptance → commit. Пароли, сертификаты и регистрации
агентов используются повторно. После commit повтор команды выполняет acceptance
без новых миграций и checkpoint.

При отказе сохраните БД, секреты, registry, recovery и каталоги transactions.
Проверьте `reason_code`, `sudo journalctl -t sli-setup`,
`sudo journalctl -u sli-reuse-check` и `result.json` транзакции.
Исправьте конфликт storage/identity/настроек; недостающий полный комплект секретов
восстановите из доверенной копии. Не переименовывайте registry/журналы и не
запускайте fresh bootstrap для обхода отказа. Незавершённую транзакцию продолжает
координатор: `sudo sli-native-upgrade resume-package <target-version>`.
После rollback требуется явная процедура согласования пакетов координатором.
После commit возврат к старому checkpoint запрещён. Для отмены репетиции
используйте полный snapshot одноразовой ВМ.

В `site.toml` необязательный `operation_stall_minutes = 15` (целое 1–180) задаёт ожидание без прогресса; без параметра миграции ждут 30 минут. Размер и история дают оценку длительности; работа продолжается при подтверждённом прогрессе.

Каталог можно выбрать флагом `--directory /srv/sli-data` до первой настройки.
Отдельный ext4-раздел, уже смонтированный в `/srv/sli-db` и настроенный в fstab,
остаётся опцией `--uuid <UUID>`; setup не создаёт разделы и не форматирует их.
Внешний каталог копий на другом диске задаётся `--backup-root /mnt/backup/sli`.
Без него режим каталога сохраняет локальные копии в `/var/backups/sli/native`:
они **не защищают от поломки диска**. Проверка восстановления требует отдельного
тома и не считается выполненной по факту создания копии. Закрытый корневой ключ
CA агентов создаётся в `/var/lib/sli-ca-offline`: перенесите этот каталог в
защищённое offline-хранилище; агентам передаются только публичные CA.

**Удаление:** `sudo apt remove sli` останавливает приложения, таймеры и БД.
Данные, `/etc/sli`, секреты и пакеты восстановления сохраняются даже при purge;
`sli-host` защищён от удаления при сохранённой установленной базе. Удаление
истории/ключей не входит в эту команду. Windows-агент удаляется через
«Установленные приложения → SLI Agent». Эти инструкции требуют проверки на
чистом Debian; исходный код и unit-тесты не являются приёмкой установки.

Для разработки используйте отдельный [dev-контейнер](CONTRIBUTING.md).

## Обновление

Для установленной беты получите новый полный комплект, описанный выше, и проверьте
`SHA256SUMS` по доверенному каналу поставки. В каталоге с его `.deb` выполните:

```sh
sudo apt install --fix-broken ./*.deb
```

Ручная настройка не нужна.
Пакетные хуки выполняют предварительные проверки, создают полную контрольную точку
и проверяют её описи, хеши и согласованность до миграций, затем выполняют миграции,
запуск и проверку здоровья. Новые транзакции записывают проверку целостности;
полное пробное восстановление запускается администратором отдельно. Транзакции,
подготовленные прежним координатором, при продолжении сохраняют требование полного
восстановления. При сбое подготовки до подтверждения контрольной точки SLI
автоматически запускает прежний релиз; ошибка повторного запуска сообщается отдельно.

Обновление выполняется как служба `sli-upgrade-*`; журнал: `sudo journalctl -u 'sli-upgrade-*'`.

Место проверяется обязательно для контрольной точки и её промежуточных файлов.
Пусть **B** — максимум размера из manifest и измеренного размера каталога
последнего успешного набора этой машины плюс положительный прирост относительно
предыдущего набора, **P** — `pg_database_size`, **F** — файлы приложения,
копируемые в промежуточный каталог, **S** — защищённые настройки, состояние
и файлы восстановления. Размеры прежних наборов пересчитываются с текущим S
перед оценкой положительного прироста. Обычная нативная копия требует
**B + F + 1 GiB** на томе копий: новый набор, промежуточные файлы и резерв.
До первой копии **B = P + F + S**, без допущения сжатия.
При остановленном PostgreSQL вместо SQL используется верхняя оценка по его файлам.
На томах живых данных остаётся отдельный резерв 1 GiB под рост.
При нехватке выводятся том, нужные и свободные байты;
можно освободить место, удалив ненужные старые наборы копий.

Для проверки восстановления из последней завершённой нативной копии выполните:

```bash
sudo systemctl start sli-backup-drill.service
sudo journalctl -u sli-backup-drill.service -f
```

Операция запускает изолированный PostgreSQL и требует дополнительно
**2B + 1,2P + 10 GiB** сверх сохранённого набора. На разных томах один B
резервируется на томе копий, остальное — на рабочем томе; на одном томе
потребности складываются. Перед восстановлением размеры проверяются снова
по фактическому набору и ZIP. Запуск службы подтверждает только начало:
дождитесь успешного завершения и `status=restore_verified`, `terminal=true`,
`databases_stopped=true` в `/var/backups/sli/native/restore-verified.json`.
Квитанция `integrity_verified` обычного обновления фиксирует отдельную проверку
содержимого; успешная проверка здоровья кандидата и завершение обновления обязательны.

После успешного завершения APT проверьте
`sudo systemctl status sli.target sli-health.service` и войдите в интерфейс.
Если APT сообщил об ошибке обновления, выполните одну команду восстановления,
напечатанную вместе с кодом причины (повтор APT — из каталога комплекта, если так
указано). Журнал: `sudo journalctl -t sli-setup`.

После обновления старой установки администратор может удалить сохранённые данные ClickHouse по своему решению: `sudo rm -rf -- /srv/sli-db/clickhouse`.

## Модель безопасности

HTTPS защищает соединения операторов и агентов. Регистрация использует
подтверждённый владельцем отпечаток ключа и краткоживущий одноразовый токен;
запросы агентов требуют mTLS и проверки реестра. Права и область доступа
платформы ограничивают отчёты и доказательства. Runtime-роли БД имеют узкие
права; миграции выполняются отдельным административным путём. Храните пароли,
токены и закрытые ключи в защищённых файлах вне репозитория. Не записывайте
секреты и приватные данные каталога в логи.

Сбор ограничен и выполняется только для чтения. Допуск удаления и копирования
в тёплый слой закрыт до явного подтверждения через эксплуатационные процедуры.
См. [политику безопасности](SECURITY.md) и [руководство администратора](docs/ADMIN_GUIDE.md).
