# SLI Platform — Security Log Intelligence

[English version](README.md)

> **Статус: в разработке.** SLI пока не готов к использованию. Первая бета-версия запланирована на **1 декабря 2026**.

SLI собирает и анализирует события безопасности Windows и данные Active Directory.
Сервер на .NET принимает данные, управляет доступом, строит отчёты и отправляет
оповещения. Первая бета проверяет Active Directory, включая групповые политики,
и обнаруживает атаки по журналам контроллеров домена.

Windows-агенты читают разрешённые источники и передают ограниченные пакеты по
HTTPS. Ядро регистрирует агентов, проверяет их через mTLS и назначает модули.
SLI только читает обследуемые системы; доступ к источникам и сбор настраиваются
явно. Установка сервера сама по себе не включает сбор.

## Архитектура

Первая бета устанавливается нативными Debian-пакетами и управляется systemd.
PostgreSQL работает на хосте.
Стек включает HTTPS API с интерфейсом React/TypeScript, сервисы миграций и
резервного копирования, воркеры обработки собранных данных, проекций, семантики,
состояния сущностей, жизненного цикла хранения, снимков AD и удалённого доступа.

- **PostgreSQL 18** — основная runtime-БД для оперативных данных, идентичностей,
  прав доступа, состояния заданий и истории миграций.
- **Агенты** получают URL сервера, публичную цепочку доверия и назначенные
  политики; им не нужны пароли БД.
- **Ядро и плагины** разделяют общие механизмы и предметные знания.

## Установка

Начните с [архива беты](#установка-из-архива). Нужен чистый **Debian 13 amd64**
с sudo и доступом к настроенным источникам APT. Планируйте 4 ядра и 8 ГБ
памяти. После установки пакетов SLI требует **20 ГиБ свободного места** на
локальном томе ext4 или XFS с доступом на запись. Для PostgreSQL локальный порт
5432 должен быть свободен на IPv4 и IPv6. Проверьте его командой
`sudo ss -ltn 'sport = :5432'`. Если порт занят, установите SLI на чистый сервер
и сохраните действующую БД. Разрешите входящий HTTPS на порт 443 или на порт,
который напечатает установщик.

### Установка из apt-репозитория

Этот способ доступен после публикации репозитория. Нужен `curl`. Оставьте
стандартные источники Debian 13 включёнными. Подписанный репозиторий SLI содержит
закреплённые пакеты PostgreSQL 18 и библиотеки, необходимые для `sli-runtime`.
Вместо `<FINGERPRINT>` укажите опубликованный полный отпечаток ключа подписи.

```sh
(
  set -eu
  keyring=$(mktemp)
  trap 'rm -f "$keyring"' EXIT
  curl -fsSL https://sli-project.github.io/sli/sli-archive-keyring.gpg -o "$keyring"
  sudo install -D -m 0644 "$keyring" /etc/apt/keyrings/sli-archive-keyring.gpg
)
printf '%s\n' 'deb [arch=amd64 signed-by=/etc/apt/keyrings/sli-archive-keyring.gpg,<FINGERPRINT>] https://sli-project.github.io/sli trixie main' | sudo tee /etc/apt/sources.list.d/sli.list >/dev/null
```

Установите пакеты и выполните первоначальную настройку:

```sh
sudo apt update && sudo apt install sli && sudo sli-setup
```

Обновление установленной SLI:

```sh
sudo apt update && sudo apt upgrade
```

Репозиторий хранит текущий и предыдущий выпуски SLI. Команда `sudo sli-rollback`
возвращает версию и данные, которые были до обновления. Если этой версии уже нет
в репозитории, передайте в `sudo sli-rollback` путь к её распакованному архиву.

### Установка из архива

Используйте опубликованный бета-выпуск с обоими файлами. Скачайте их в пустой
каталог под вашим управлением. Оставьте место для скачивания, распакованного
комплекта и его временной копии в `/tmp`.

1. Скопируйте тег `beta-…` из предварительного выпуска в разделе
   [Releases](https://github.com/sli-project/sli/releases) и подставьте его вместо
   `beta-COMMIT12` в команде ниже.
   В описании выпуска указаны исходный коммит и ссылка на сборку GitHub Actions.
   Выполните команду в каталоге загрузки, чтобы скачать `sli-debian-beta-kit.tar.gz`
   и `SHA256SUMS` из одного выпуска и проверить архив перед распаковкой.

   ```sh
   tag=beta-COMMIT12
   curl -LO --fail "https://github.com/sli-project/sli/releases/download/$tag/sli-debian-beta-kit.tar.gz" &&
   curl -LO --fail "https://github.com/sli-project/sli/releases/download/$tag/SHA256SUMS" &&
   sha256sum --check SHA256SUMS && tar -xzf sli-debian-beta-kit.tar.gz
   ```

2. В каталоге, где распаковали архив, выполните:

   ```sh
   bash sli-debian-beta-kit/install-beta-kit
   ```

   Скрипт сверяет распакованные манифест, скрипты и `.deb` по внутреннему
   `SHA256SUMS`, обновляет списки из настроенных источников APT и устанавливает
   пакеты. Он сохраняет более новые сторонние пакеты и предотвращает создание
   стандартного кластера PostgreSQL. Адрес, порт и диск выбираются автоматически,
   если не задать параметры ниже.

### Первый вход

Дождитесь успешного завершения настройки и откройте напечатанный HTTPS-адрес.
В Windows выполните строку PowerShell из доверенной консоли сервера. Она
добавит публичный CA в хранилище доверия вашей учётной записи и откроет адрес.
На других системах скопируйте `/var/lib/sli/tls-ca.crt` с доверенного сервера,
сверьте отпечаток SHA-256 с выводом настройки и импортируйте сертификат в
хранилище доверия браузера. На Debian отпечаток можно вывести повторно.

```sh
openssl x509 -in /var/lib/sli/tls-ca.crt -noout -fingerprint -sha256
```

Проверьте, что напечатанный адрес разрешается и доступен с вашего ПК и
контроллера домена. На чистой установке войдите с логином и паролем `admin`,
задайте пароль длиной от 12 символов и [подключите контроллер домена](#агент-windows).

### Необязательные параметры установки

Передайте параметры скрипту `install-beta-kit`. Если пакеты уже установлены,
передайте их в `sudo sli-setup`.

- `--server`, `--port` и `--bind` задают внешний адрес, порт HTTPS и адрес
  прослушивания. До настройки проверьте доступность постоянного DNS-имени или
  статического IP с рабочего ПК и контроллера домена. Укажите `--server` без
  схемы и порта. Если имя не разрешается, setup сообщит о подстановке IP или
  остановится, если подходящего адреса нет. Если 443 занят при первом setup без `--port`,
  setup выберет свободный порт. Конфликт указанного или сохранённого порта
  останавливает настройку.
- Без параметров хранилища setup выбирает подходящий локальный том ext4 или XFS
  с наибольшим свободным местом. При равенстве выбирает `/var/lib/sli-db`.
  Setup исключает том копий и сохраняет существующие данные. Для
  `--directory /mnt/data/sli-db` смонтируйте том в `/mnt/data`, выделите пустой
  каталог для SLI и оставьте `/srv/sli-db` свободным для привязки. Для `--uuid`
  смонтируйте доступный на запись том ext4 прямо в `/srv/sli-db` и передайте
  UUID файловой системы. Сохраните монтирование после перезагрузки. Проверьте
  указанный том, точку монтирования и свободное место командами `lsblk -f`,
  `findmnt` и `df -h`.
- Подготовьте внешние тома до первой настройки. Для `--backup-root /mnt/backup/sli`
  нужен существующий защищённый каталог на отдельной от БД файловой системе,
  место для первой копии и свободная точка монтирования `/var/backups/sli`.
  Для `--cold-tablespace-root` нужен существующий защищённый каталог под `/mnt`
  или `/srv` на отдельном доступном на запись ext4 или XFS с UUID. Каталоги и
  их родители должны принадлежать root, разрешать запись только root и быть
  доступны без символьных ссылок. Для каталога холодных таблиц и его родителей
  PostgreSQL нужен доступ на проход. С `--uuid` храните копии на отдельной от БД
  файловой системе. Если стандартный путь копий на томе БД, задайте `--backup-root`.
- `sudo sli-setup --reset-admin-password` возвращает пароль владельца `admin`,
  отзывает действующие сессии и требует сменить пароль при следующем входе.
  Имя владельца сохраняется.
- Для заблокированного владельца выполните `sudo sli-setup --owner-recovery <имя-владельца>`
  в root-консоли сервера. На свежей установке укажите `admin`, после обновления —
  прежнее имя владельца. На странице входа откройте **Аварийный вход владельца**.
  В течение 10 минут введите одноразовый код в поле **Код восстановления**
  вместе с действующим паролем. Выпуск нового кода отменяет предыдущий. Восстановление
  доступно активному владельцу платформы. Пароль и блокировка обычного входа
  сохраняются.

По умолчанию SLI слушает IPv4 и, когда доступен, IPv6. Сертификат охватывает
имя сервера, его разрешённые адреса и loopback. Параметр `--bind 192.0.2.10`
ограничивает HTTPS одним локальным адресом. Проверки готовности идут на этот
адрес. Для локального обратного прокси используйте `--bind 127.0.0.1` и настройте
доверенные прокси. После смены адреса по DHCP обновите DNS и сохраните прежний
URL с DNS-именем и привязкой по умолчанию. При установке по IP сохраните исходный
статический адрес.

Повторяйте настройку с прежними параметрами. При конфликте сохранённых имени,
привязки, порта или путей setup выдаёт `native_setup_configuration_conflict`.
Если первый запуск прервался до записи
установки и повтор вернул `native_install_interrupted_requires_recovery`,
сохраните БД и состояние установки. Запишите причину, флаги setup и точки
монтирования. Соберите журналы настройки и служб.

```sh
sudo journalctl -b -t sli-setup
sudo journalctl -b -u sli-postgresql.service -u sli-bootstrap-pg.service -u sli-ready.service -u sli-health.service
```

### Агент Windows

1. Войдите как владелец платформы или с правом `access.manage`. Пока агенты
   не зарегистрированы, нажмите **Добавить агента** на **Главной**. Кнопка также
   доступна в разделе **Агенты**.
2. Укажите HTTPS-адрес, доступный напрямую с Windows, например
   `https://sli.example.test:8443`, без `/app`. Имя или IP должны входить в
   сертификат сервера. Команда подключается без прокси и перенаправлений.
   Выберите от 1 до 100 компьютеров (по умолчанию 1).
   Оставьте управление аудитом включённым, чтобы SLI настроила аудит Windows
   на контроллере домена. При ошибке адреса выберите имя или IP из сообщения.
   Если форма не загрузила параметры или пакет, проверьте MSI и сертификат
   на сервере и откройте её снова.
3. Нажмите **Создать команду** и выполните скопированную строку в 64-разрядном
   PowerShell от имени администратора на контроллере домена. Интерфейс сохранит
   адрес. Строка содержит секретный ключ регистрации на один час. Он допускает
   по одной регистрации на компьютер в пределах выбранного числа. Передавайте
   её только администратору, который установит агент. По истечении срока или
   лимита создайте новую команду. Скрипт проверяет TLS и хеш MSI до установки.
4. После запуска службы проверьте **Последняя связь** в разделе **Агенты**,
   чтобы подтвердить регистрацию. Затем откройте **Состояние системы → Первый
   запуск** по адресу `/app/admin/status` и дождитесь строки **Первые данные:
   получены в …**. После завершения первого запуска смотрите колонку
   **Последние данные** своего компьютера в таблице **Источники** на этой же
   странице. Отдельно проверьте отчёты AD и групповых политик. Для их снимков
   нужна подтверждённая область домена контроллера.
5. Откройте **Оповещения → Каналы** (`/app/notifications?tab=channels`), настройте
   канал, нажмите **Отправить проверку** и убедитесь, что сообщение пришло.

На сервере `sudo sli-agent-command` использует сохранённый адрес. В примере
адрес задаётся только для текущей команды.

```sh
sudo sli-agent-command --server-url https://sli.example.test:8443 --count 1
```

Подставьте HTTPS-адрес своего сервера. Если адрес не сохранён, передавайте
`--server-url` при каждом вызове. `--count` принимает 1–100, а `--no-audit`
оставляет управление аудитом выключенным.

Для отдельной проверки MSI используйте PowerShell на компьютере, который
доверяет CA сервера. Подставьте в URL HTTPS-адрес своего сервера.

```powershell
curl.exe -fsS -D - -o SliAgent.msi https://sli.example.test:8443/api/v1/agent/installer/SliAgent.msi
Get-FileHash .\SliAgent.msi -Algorithm SHA256
```

Сверьте выведенный заголовок `X-SLI-Package-SHA256` с хешем файла. Для первой
регистрации используйте созданную команду.

Для плановой замены стандартной MSI-установки выпустите новую команду для этого
компьютера, затем снова проверьте связь и первые данные. Если для существующей
регистрации требуется одобрение владельца, получите его до замены. При сообщении
о нестандартном каталоге состояния, `agent.json` или оставшейся старой службе
сохраните настройки и состояние агента и устраните указанную причину перед
повтором. Держите под рукой прежний MSI. Если замена прервётся после его
удаления, он может понадобиться для восстановления службы Windows.

### Нативные резервные копии

Проверьте ежедневный таймер, затем создайте первую копию и прочитайте результат.

```sh
sudo systemctl list-timers sli-backup.timer
sudo sli-backup && sudo cat /var/backups/sli/native/last-result.json
```

Команда печатает каталог готового набора. Сверьте его имя с `backup_id` при
`status=backup_created` и `terminal=true`. Храните прежние проверенные наборы,
пока новый не пройдёт [пробное восстановление](#обновление). Без внешнего тома
копий режим каталога допускает локальные копии в `/var/backups/sli/native`.
Внешний том SLI подключает в `/var/backups/sli`. Проверьте
[требования к месту](#обновление) на файловой системе, где хранятся копии.

### Восстановление и откат

`sudo sli-restore <каталог-копии>` восстанавливает данные и настройки с тем же
комплектом Debian, которым создан набор. Каталог копии и всё его содержимое
должны принадлежать root и быть недоступны другим пользователям. Используйте
обычные файлы без дополнительных жёстких ссылок и каталоги без символических
ссылок. Незавершённое восстановление повторяйте с тем же набором.

На чистом сервере проверьте и распакуйте архив того же комплекта, как описано
выше. Из распакованного комплекта установите только пакеты.

```sh
sha256sum --check --strict SHA256SUMS && sudo apt-get update && sudo apt-get install --no-remove ./*.deb
```

Перенесите на новый сервер весь каталог, включая `manifest.json`. Сохраните
владельца и права по требованиям выше. Запустите `sli-restore` с каталогом
копии. Оставьте первичную настройку команде восстановления, поскольку
`sli-setup` и `install-beta-kit` инициализируют новую установку.
Восстановление использует режим каталога, локальные копии и табличное
пространство PostgreSQL по умолчанию. Сохраните прежнее DNS-имя или IP для
действующих сертификатов агентов. Если в копии есть сохранённые учётные данные
AD, заранее подготовьте их исходный защищённый ключ на новом сервере.

Перед обновлением сохраните проверенный прежний комплект. Сохраните также
контрольную копию, которую создаёт обновление. После завершённого обновления
`sudo sli-rollback <каталог-прежнего-комплекта>` использует эту копию и прежнюю
среду выполнения. Без каталога `sudo sli-rollback` запрашивает в APT точные
прежние версии `sli`, `sli-host`, `sli-rollback-hold` и `sli-server-dotnet`.
При сбое обновления используйте [порядок восстановления](#обновление).

Перед заменой действующих данных обе команды сохраняют их в
`/var/backups/sli/native/before-restore/<ID-транзакции>/<ID-копии>`.
Прочитайте `/var/lib/sli/transactions/<ID-транзакции>/result.json`. Успешное
восстановление даёт `status=committed`, откат — `status=rolled_back`.
В обоих случаях требуется `services_restored=true`.

### Переустановка с сохранением данных

На том же подготовленном сервере сохраните все БД, настройки, секреты, CA
агентов, реестр в `/var/lib/sli`, защищённые файлы восстановления и проверенный
прежний комплект. Проверьте и распакуйте полный новый комплект Debian. В его
каталоге сверьте внутренние
контрольные суммы и проверьте план APT перед удалением `sli`.

```sh
sha256sum --check --strict SHA256SUMS && sudo apt-get update && sudo apt-get -s install --no-remove ./*.deb
```

Выберите комплект, зависимости которого разрешаются без понижения версий
сторонних пакетов. Запустите переустановку из того же каталога.

```bash
sudo apt remove sli && sudo apt-get install --no-remove ./*.deb && sudo sli-setup --reuse-existing
```

Удаление останавливает SLI и его БД, сохраняя данные. Пакеты подготавливают
новый выпуск. Setup проверяет сохранённую установку, блокирует запись, создаёт
полную контрольную точку и проверяет её содержимое и согласованность. Затем
выполняет миграции, проверяет службы и активирует выпуск. Запускайте
[пробное восстановление](#обновление) отдельно. Пароли, сертификаты
и регистрации агентов сохраняются. После завершения повтор команды проверяет
службы без новой миграции и контрольной точки.

При отказе сохраните БД, секреты, реестр, файлы восстановления и каталоги
транзакций. Проверьте `reason_code`, `sudo journalctl -t sli-setup`,
`sudo journalctl -u sli-reuse-check` и `result.json` транзакции. Устраните
конфликт хранилища, идентичности или настроек. Недостающий комплект секретов
восстановите из доверенной копии. Сохраните исходные имена реестра и журналов.
Для незавершённой транзакции выполните
`sudo sli-native-upgrade resume-package <target-version>`. После ошибки APT
следуйте порядку согласования пакетов. После успешного обновления для отката
используйте `sudo sli-rollback`.

В `site.toml` параметр `operation_stall_minutes` принимает целое число от 1 до
180 и задаёт ожидание без прогресса. По умолчанию для миграций это 30 минут.
Используйте значение, сохранённое при установке. После ручной правки файла
setup или переустановка могут отклонить конфигурацию. Перенесите
`/var/lib/sli-ca-offline` в защищённое автономное хранилище. Агентам передавайте
только публичные CA.

### Удаление

`sudo sli-remove` останавливает SLI и удаляет её пакеты и юниты systemd. БД,
настройки, ключи и файлы восстановления сохраняются. Для старой установки без
`sli-remove` выполните `sudo python3 -I ./remove-beta-kit` из распакованного
каталога проверенного текущего комплекта.

Чтобы стереть локальные данные SLI, выполните `sudo sli-remove --purge-data`
или `sudo python3 -I ./remove-beta-kit --purge-data` для старой установки.
Сначала проверьте, что смонтированы нужные тома БД и холодных таблиц. Флаг
удаляет локальные БД, настройки, ключи, автономный CA на сервере, локальные
копии и управляемый каталог холодных таблиц. Общие пакеты Debian и БД, внешние
тома резервных копий и копии в автономном хранилище сохраняются.

В Windows откройте **Установленные приложения** и удалите **SLI Agent .NET**.
Его служба называется `SLIAgentNet`. Запись **SLI Agent** относится к старому MSI.
Чтобы отозвать и регистрацию на сервере, откройте компьютер в разделе
**Агенты** и выберите **Отключить агента**.

Для разработки используйте отдельный [dev-контейнер](CONTRIBUTING.md).

## Обновление

Публичные комплекты беты начинают отдельную цепочку контрольных сумм миграций.
Для БД из частной цепочки используйте чистую установку. Установленную публичную
бету обновляйте тем же способом, которым установили. Для APT используйте
[команду обновления APT](#установка-из-apt-репозитория). При установке из архива
скачайте и проверьте новый комплект, как описано выше.
Запустите установщик из распакованного каталога с `.deb`, `SHA256SUMS` и
`install-beta-kit`.

```sh
bash ./install-beta-kit
```

Скрипт архива запускает `sli-setup` после APT. Дождитесь успешного завершения
обоих этапов. Установка из архива не добавляет источник SLI в APT.
Пакетные хуки выполняют предварительные проверки, создают полную контрольную точку
и проверяют её описи, хеши и согласованность до миграций, затем выполняют миграции,
запуск и проверку здоровья. Новые транзакции записывают проверку целостности;
полное пробное восстановление запускается администратором отдельно. Транзакции,
подготовленные прежним координатором, при продолжении сохраняют требование полного
восстановления. При сбое подготовки до подтверждения контрольной точки SLI
автоматически запускает прежний релиз; ошибка повторного запуска сообщается отдельно.

Обновление выполняется как служба `sli-upgrade-*`; журнал: `sudo journalctl -u 'sli-upgrade-*'`.

Место проверяется обязательно для контрольной точки и её промежуточных файлов.
Пусть **B** — максимум размера из manifest и измеренного размера каталога
последнего успешного набора этой машины плюс положительный прирост относительно
предыдущего набора, **P** — `pg_database_size`, **F** — файлы приложения,
копируемые в промежуточный каталог, **S** — защищённые настройки, состояние
и файлы восстановления. Размеры прежних наборов пересчитываются с текущим S
перед оценкой положительного прироста. Обычная нативная копия требует
**B + F + 1 GiB** на томе копий: новый набор, промежуточные файлы и резерв.
До первой копии **B = P + F + S**, без допущения сжатия.
При остановленном PostgreSQL вместо SQL используется верхняя оценка по его файлам.
На томах живых данных остаётся отдельный резерв 1 GiB под рост.
Проверьте свободное место на фактических файловых системах копий и БД.

```sh
df -h /var/backups/sli/native /srv/sli-db
```

При нехватке выводятся том, нужные и свободные байты. Сохраните набор из поля
`backup_id` в `/var/backups/sli/native/restore-verified.json`. Пока нужен откат,
храните контрольную копию
из поля `checkpoint` в `journal.json` обновления. Текущие контрольные копии
хранятся в `/var/backups/sli/native/upgrade-checkpoints/<ID-транзакции>`.

Перед пробным восстановлением создайте хотя бы одну успешную копию. Копии и
рабочий каталог (по умолчанию `/var/backups/sli/restore-check`) должны быть на
файловых системах отдельно от рабочей БД. Запишите `backup_id` последнего набора,
затем запустите пробное восстановление и следите за журналом.

```bash
sudo systemctl start sli-backup-drill.service
sudo journalctl -u sli-backup-drill.service -f
```

Операция запускает изолированный PostgreSQL и требует дополнительно
**2B + 1,2P + 10 GiB** сверх сохранённого набора. На разных томах один B
резервируется на томе копий, остальное — на рабочем томе; на одном томе
потребности складываются. По завершении прочитайте
`sudo cat /var/backups/sli/native/drill-result.json`. Сверьте ожидаемый
`backup_id`, время `completed_at_utc` текущего запуска и поля
`status=restore_verified`, `terminal=true`, `databases_stopped=true`. Сверьте
`manifest_sha256` с `sudo sha256sum /var/backups/sli/native/<backup-id>/manifest.json`
для этого набора.
Квитанция `integrity_verified` обычного обновления фиксирует отдельную проверку
содержимого; успешная проверка здоровья кандидата и завершение обновления обязательны.

После завершения обновления проверьте `sudo systemctl status sli.target sli-health.service`
и ожидаемую версию на странице **Состояние системы**. Для нового выпуска
проверьте `status=committed` и `services_restored=true` в результате транзакции.
При сбое запишите код причины, проверьте журналы
`sli-upgrade-*` и `sli-setup` и найдите результат этой попытки.

```sh
sudo find /var/lib/sli/transactions -name result.json -printf '%T@ %p\n' | sort -nr | head
```

Если координатор указал `resume-package`, после выхода APT выполните
напечатанную команду `sudo sli-native-upgrade resume-package <target-version>`.
Значение `target_version` есть в `journal.json` транзакции. В каталоге комплекта
`dpkg-deb -f ./sli_*.deb Version` покажет версию пакета `sli`. Для APT-обновления
`apt-cache policy sli` покажет версию-кандидат.
Перезапуск прежнего выпуска и согласование установленных пакетов выполняются
отдельно. После отката для согласования могут понадобиться прежние версии
`.deb` в источниках APT. Если транзакция ещё не создана, устраните указанную
причину и повторите обновление исходным способом.

После обновления старой установки храните данные ClickHouse до конца срока
отката. Перед очисткой проверьте, что каталог принадлежит SLI на нужном
смонтированном томе и что отдельная копия содержит нужную историю ClickHouse.

## Модель безопасности

HTTPS защищает соединения операторов и агентов. Команда установки использует
ограниченный по времени ключ регистрации с лимитом по числу компьютеров.
Для ручной регистрации нужны подтверждённый владельцем отпечаток ключа и
одноразовый токен. Запросы агентов требуют mTLS и проверки реестра. Права и
область доступа платформы ограничивают отчёты и доказательства. Runtime-роли БД имеют узкие
права; миграции выполняются отдельным административным путём. Храните пароли,
токены и закрытые ключи в защищённых файлах вне репозитория. Не записывайте
секреты и приватные данные каталога в логи.

Сбор ограничен и выполняется только для чтения. Допуск удаления и копирования
в тёплый слой закрыт до явного подтверждения через эксплуатационные процедуры.
См. [политику безопасности](SECURITY.md) и [руководство администратора](docs/ADMIN_GUIDE.md).
