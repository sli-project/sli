# Обновление, резервное копирование, откат и восстановление

[English version](../en/upgrade.md) · [Руководства](README.md)

## Обновление

Публичные комплекты беты начинают отдельную цепочку контрольных сумм миграций.
Для БД из частной цепочки используйте чистую установку. Установленную публичную
бету обновляйте тем же способом, которым установили. Для APT используйте
[команду обновления APT](install.md#обновление-через-apt). При установке из архива
[скачайте и проверьте новый комплект](install.md#скачайте-и-проверьте-архив).
Запустите установщик из распакованного каталога с `.deb`, `SHA256SUMS` и
`install-beta-kit`.

```sh
bash ./install-beta-kit
```

Скрипт архива запускает `sli-setup` после APT. Дождитесь успешного завершения
обоих этапов. Установка из архива не добавляет источник SLI в APT.
Пакетные хуки выполняют предварительные проверки, создают полную контрольную точку
и проверяют её описи, хеши и согласованность до миграций, затем выполняют миграции,
запуск служб и проверку их здоровья. В новых транзакциях записывается результат
проверки целостности. Полное пробное восстановление запускается отдельно.
Транзакции, подготовленные прежним координатором, при продолжении сохраняют
требование полного восстановления. При сбое подготовки до подтверждения контрольной точки SLI
автоматически запускает прежний выпуск и сообщает об ошибке повторного запуска.

Журнал службы обновления `sli-upgrade-*` можно открыть командой
`sudo journalctl -u 'sli-upgrade-*'`.

### Проверьте свободное место

Место проверяется обязательно для контрольной точки и её промежуточных файлов.
Пусть **B** — максимум размера из manifest и измеренного размера каталога
последнего успешного набора этой машины плюс положительный прирост относительно
предыдущего набора, **P** — `pg_database_size`, **F** — файлы приложения,
копируемые в промежуточный каталог, **S** — защищённые настройки, состояние
и файлы восстановления. Размеры прежних наборов пересчитываются с текущим S
перед оценкой положительного прироста. Обычная нативная копия требует
**B + F + 1 GiB** на томе копий: новый набор, промежуточные файлы и резерв.
До первой копии **B = P + F + S**, без допущения сжатия.
При остановленном PostgreSQL вместо SQL используется верхняя оценка по его файлам.
На томах живых данных остаётся отдельный резерв 1 GiB под рост.
Проверьте свободное место на фактических файловых системах копий и БД.

```sh
df -h /var/backups/sli/native /srv/sli-db
```

При нехватке выводятся том, нужные и свободные байты. Пока нужен откат,
храните контрольную копию
из поля `checkpoint` в `journal.json` обновления. Текущие контрольные копии
хранятся в `/var/backups/sli/native/upgrade-checkpoints/<ID-транзакции>`.

Квитанция `integrity_verified` фиксирует проверку содержимого. Для обновления
также требуются успешная проверка здоровья кандидата и коммит.

### Проверьте результат или продолжите обновление

После завершения обновления проверьте `sudo systemctl status sli.target sli-health.service`
и ожидаемую версию на странице **Состояние системы**. Для нового выпуска
проверьте `status=committed` и `services_restored=true` в результате транзакции.
При сбое запишите код причины, проверьте журналы
`sli-upgrade-*` и `sli-setup` и найдите результат этой попытки.

```sh
sudo find /var/lib/sli/transactions -name result.json -printf '%T@ %p\n' | sort -nr | head
```

Дождитесь выхода APT, прежде чем продолжить транзакцию или согласовать пакеты.
Возьмите целевую версию из команды восстановления, напечатанной установщиком,
и сверьте её с `target_version` в `journal.json` этой транзакции. В каталоге
комплекта `dpkg-deb -f ./sli_*.deb Version` покажет версию пакета `sli`.
Для обновления через APT команда `apt-cache policy sli` покажет версию-кандидат.

- Если транзакция не завершена и координатор указал `resume-package`,
  выполните напечатанную команду
  `sudo sli-native-upgrade resume-package <target-version>`.
- Если в `journal.json` указаны `status=rolled_back`, `step=after` и
  `services_restored=true`, а в `result.json` указано
  `package_reconciliation_required=true`, выполните
  `sudo sli-native-upgrade reconcile <target-version>`. Для согласования
  нужны точные прежние версии пакетов `sli`, `sli-host` и
  `sli-rollback-hold` из настроенных источников APT. Сохраните проверенный
  прежний комплект, чтобы при необходимости взять из него пакеты этих версий.
  Если эти версии недоступны APT, согласование пакетов остаётся незавершённым.
- Если транзакция ещё не создана, устраните указанную причину и повторите
  обновление исходным способом.

После согласования сверяйте в обоих файлах один и тот же `transaction`,
`status=rolled_back` и ожидаемый прежний выпуск в `accepted_release`. В `journal.json`
сверьте `step=after` и `services_restored=true`, а в `result.json` —
`terminal=true` и `package_reconciliation_required=false`. Проверьте службы
и восстановленную версию на странице **Состояние системы**, как описано выше.

После обновления старой установки храните данные ClickHouse до конца срока
отката. Перед очисткой проверьте, что каталог принадлежит SLI на нужном
смонтированном томе и что отдельная копия содержит нужную историю ClickHouse.

## Нативные резервные копии

В разделе **Настройки → Резервное копирование** выберите подготовленный каталог
на подключённой локальной файловой системе на другом диске, чем базы данных. При новой
установке ежедневное расписание выключено. Включите его для автоматического
копирования. Команда `sudo sli-backup` создаёт копию на выбранном томе и при
выключенном расписании.

Если выбран `/mnt/sli-archives`, следующие команды проверяют таймер и показывают
результат ручного копирования.

```sh
sudo systemctl list-timers sli-backup.timer
sudo sli-backup && sudo cat /mnt/sli-archives/sli-regular-backups/last-result.json
```

Команда печатает каталог готового набора. Сверьте его имя с `backup_id` при
`status=backup_created` и `terminal=true`. Храните набор, указанный в
`restore-verified.json` в каталоге архивов, пока новый не пройдёт
[пробное восстановление](#пробное-восстановление). Проверьте
[требования к месту](#проверьте-свободное-место) на выбранной файловой системе.
Если том недоступен или подменён, регулярные копии не создаются. Контрольные
точки обновления хранятся в `/var/backups/sli/native/upgrade-checkpoints`.

### Пробное восстановление

Перед пробным восстановлением создайте хотя бы одну успешную копию. Копии и
рабочий каталог (по умолчанию `/var/backups/sli/restore-check`) должны быть на
файловых системах отдельно от рабочей БД. Запишите `backup_id` последнего набора,
затем запустите пробное восстановление и следите за журналом.

```bash
sudo systemctl start sli-backup-drill.service
sudo journalctl -u sli-backup-drill.service -f
```

Операция запускает изолированный PostgreSQL и требует дополнительно
**2B + 1,2P + 10 GiB** сверх сохранённого набора. Для этой проверки B —
измеренный размер выбранного набора, P — размер PostgreSQL из его манифеста.
На разных томах один B резервируется на томе копий, остальное — на рабочем
томе. Если копия и рабочий каталог находятся на одной файловой системе,
сложите потребности. По завершении прочитайте
`sudo cat /mnt/sli-archives/sli-regular-backups/drill-result.json`, подставив
выбранный путь. Сверьте ожидаемый
`backup_id`, время `completed_at_utc` текущего запуска и поля
`status=restore_verified`, `terminal=true`, `databases_stopped=true`. Сверьте
`manifest_sha256` с
`sudo sha256sum /mnt/sli-archives/sli-regular-backups/<backup-id>/manifest.json`
для этого набора.

## Восстановление и откат

### Восстановление из резервной копии

`sudo sli-restore <каталог-копии>` восстанавливает данные и настройки с тем же
комплектом Debian, которым создан набор. Каталог копии и всё его содержимое
должны принадлежать root и быть недоступны другим пользователям. Используйте
обычные файлы без дополнительных жёстких ссылок и каталоги без символических
ссылок. Незавершённое восстановление повторяйте с тем же набором.

На чистом сервере [проверьте и распакуйте архив того же комплекта](install.md#скачайте-и-проверьте-архив).
Из распакованного комплекта установите только пакеты.

```sh
sha256sum --check --strict SHA256SUMS && sudo apt-get update && sudo apt-get install --no-remove ./*.deb
```

Перенесите на новый сервер весь каталог, включая `manifest.json`. Сохраните
владельца и права по требованиям выше. Выполните `sudo sli-restore <каталог-копии>`
для перенесённой копии. Команда восстановления сама выполнит первичную настройку.
Восстановление использует режим каталога, локальные копии и табличное
пространство PostgreSQL по умолчанию. Сохраните прежнее DNS-имя или IP для
действующих сертификатов агентов. Если в копии есть сохранённые учётные данные
AD, заранее подготовьте их исходный защищённый ключ на новом сервере.

### Откат обновления

Перед обновлением сохраните проверенный прежний комплект. Сохраните также
контрольную копию, которую создаёт обновление. После завершённого обновления
`sudo sli-rollback <каталог-прежнего-комплекта>` использует эту копию и прежнюю
среду выполнения. Без каталога `sudo sli-rollback` запрашивает в APT точные
прежние версии `sli`, `sli-host`, `sli-rollback-hold` и `sli-server-dotnet`.
При сбое обновления используйте [порядок восстановления](#проверьте-результат-или-продолжите-обновление).

### Проверьте результат восстановления или отката

Перед заменой действующих данных обе команды сохраняют их в
`/var/backups/sli/native/before-restore/<ID-транзакции>/<ID-копии>`.
Прочитайте `/var/lib/sli/transactions/<ID-транзакции>/result.json`. Успешное
восстановление даёт `status=committed`, откат — `status=rolled_back`.
В обоих случаях требуется `services_restored=true`.

## Переустановка с сохранением данных

На том же подготовленном сервере сохраните все БД, настройки, секреты, CA
агентов, реестр в `/var/lib/sli`, защищённые файлы восстановления и проверенный
прежний комплект. Проверьте и распакуйте полный новый комплект Debian. В его
каталоге сверьте внутренние
контрольные суммы и проверьте план APT перед удалением `sli`.

```sh
sha256sum --check --strict SHA256SUMS && sudo apt-get update && sudo apt-get -s install --no-remove ./*.deb
```

Выберите комплект, зависимости которого разрешаются без понижения версий
сторонних пакетов. Запустите переустановку из того же каталога.

```bash
sudo apt remove sli && sudo apt-get install --no-remove ./*.deb && sudo sli-setup --reuse-existing
```

Удаление останавливает SLI и его БД, сохраняя данные. Пакеты подготавливают
новый выпуск. Setup проверяет сохранённую установку, блокирует запись, создаёт
полную контрольную точку и проверяет её содержимое и согласованность. Затем
выполняет миграции, проверяет службы и активирует выпуск. Запускайте
[пробное восстановление](#пробное-восстановление) отдельно. Пароли, сертификаты
и регистрации агентов сохраняются. После завершения повтор команды проверяет
службы без новой миграции и контрольной точки.

При отказе сохраните БД, секреты, реестр, файлы восстановления и каталоги
транзакций. Проверьте `reason_code`, `sudo journalctl -t sli-setup`,
`sudo journalctl -u sli-reuse-check` и `result.json` транзакции. Устраните
конфликт хранилища, идентичности или настроек. Недостающий комплект секретов
восстановите из доверенной копии. Сохраните исходные имена реестра и журналов.
Для незавершённой транзакции выполните
`sudo sli-native-upgrade resume-package <target-version>`. После ошибки APT
следуйте порядку согласования пакетов. После успешного обновления для отката
используйте `sudo sli-rollback`.

В `site.toml` параметр `operation_stall_minutes` принимает целое число от 1 до
180 и задаёт ожидание без прогресса. По умолчанию для миграций это 30 минут.
Используйте значение, сохранённое при установке. После ручной правки файла
setup или переустановка могут отклонить конфигурацию. Перенесите
`/var/lib/sli-ca-offline` в защищённое автономное хранилище. Агентам передавайте
только публичные CA.

## Удаление

`sudo sli-remove` останавливает SLI и удаляет её пакеты и юниты systemd. БД,
настройки, ключи и файлы восстановления сохраняются. Для старой установки без
`sli-remove` выполните `sudo ./remove-beta-kit` из распакованного
каталога проверенного текущего комплекта.

Чтобы стереть локальные данные SLI, выполните `sudo sli-remove --purge-data`
или `sudo ./remove-beta-kit --purge-data` для старой установки.
Сначала проверьте, что смонтированы нужные тома БД и холодных таблиц. Флаг
удаляет локальные БД, настройки, ключи, автономный CA на сервере, локальные
копии и управляемый каталог холодных таблиц. Общие пакеты Debian и БД, внешние
тома резервных копий и копии в автономном хранилище сохраняются.

Удаление агента Windows описано в [руководстве по агенту](agents.md#удаление-агента).

Для разработки используйте отдельный [dev-контейнер](../../CONTRIBUTING.md).
